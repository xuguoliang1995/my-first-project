# 0001 记录架构决策

- 状态：已采纳
- 日期：2026-10-29
- 关联变更：无（骨架初始化）

## 背景

AI 编码中最贵的成本不是写代码，而是**三个月后没人知道当初为什么这么做**。
智能体每次会话都没有上一次的记忆，如果决策只存在于对话里，
下一次它就会用另一套方案重写一遍，产生不兼容的重复实现。

## 决策

所有影响架构的取舍都写成本目录下的一条 ADR：

- 文件名：`NNNN-短横线标题.md`，编号连续递增
- 状态取值：`提议中` / `已采纳` / `已废弃` / `被 NNNN 取代`
- 一条 ADR 只记录**一个**决策
- 已采纳的 ADR 不修改结论；结论变了就新开一条并在旧条目标注"被 NNNN 取代"

## 什么必须写 ADR

- 技术栈选型（框架、数据库、ORM、状态管理）
- 跨包契约的设计（`packages/shared` 的类型结构）
- 数据模型与迁移策略
- 鉴权与权限模型（含 2FA、恢复流程）
- 引入重要依赖或放弃既有方案

## 什么不需要写

- 单文件内的实现细节
- 可被 lint / 类型系统约束的规范（属于 `harness/rules/`）
- 尚未落地的设想（等真正要采用时再写）

## 理由与取舍

**选择 ADR 而非把决策写进代码注释**：注释跟着代码走，重构时容易丢；
ADR 是时间线，保留被否决的方案，这对后续判断"为什么不能走那条路"同样关键。

**选择记录被放弃的方案**：只写结论的决策记录会在半年后变成无法质疑的教条。
写出"放弃了什么、为什么放弃"，才能在新条件下重新评估。

## 后果

**正面：** 决策可追溯；新会话能快速理解约束；被否决的方案不会反复被重新提出。

**负面：** 需要持续维护；ADR 与实现脱节时会误导后来者（靠评审和归档时同步缓解）。

## 适用条件

- 项目拥有多个会话、多个参与者，或需要长期维护

## 失效条件

- 一次性原型、代码生命周期短于一周的探索性验证
