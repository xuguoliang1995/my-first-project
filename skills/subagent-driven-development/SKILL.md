# 技能：subagent-driven-development（子智能体执行）

## 核心价值

子智能体不是"更快的手"，而是**隔离的上下文**：

- 主上下文只保留结论，不保留搜索过程与试错细节
- 每个子任务拿到干净、聚焦的上下文，不被历史噪音干扰
- 互不依赖的任务可并行，压缩总耗时

## 何时用

| 适合 | 不适合 |
| --- | --- |
| 任务清单已就绪，任务间无共享状态 | 需要全局一致的重构（改名、改契约） |
| 探索性搜索（"这个功能在哪实现的"） | 任务 B 依赖任务 A 的即时输出 |
| 独立模块的实现 | 需要频繁与用户确认的模糊需求 |
| 并行的代码评审与测试补全 | 单文件小改动（收益低于开销） |

## 步骤

### 1. 明确契约（先于派发）

给子智能体写清四件事，缺一不可：

```
目标：做什么，边界在哪（不做什么）
输入：可读的文件、可用的命令
产出：返回什么格式（结论 / 文件路径 / 测试结果）
验收：怎么判断它做对了
```

模糊派发的成本 = 子智能体凭空发挥 + 你重新审一遍。

### 2. 一个任务一个子智能体

不要把 5 个任务塞给一个子智能体——它会退化成"看起来都做了"。
任务边界清楚时，宁可多派几个。

### 3. 并行判断

可以并行：只读的探索、互不相交的模块实现、独立的评审。
必须串行：有共享文件、有依赖顺序、结果会影响下一步决策。

**并行写文件时确保文件集合不相交**，否则会互相覆盖。

### 4. 验收子智能体的产出

不看它的自述，看**证据**：

- 声称改了文件 → 自己读一遍关键部分
- 声称测试通过 → 自己跑一次相关命令
- 声称"已完成" → 对照任务清单逐项核对

### 5. 汇总

主上下文只记录：做了什么、哪些文件、验证结果、遗留问题。
不要复述子智能体的完整过程。

## 本项目中的定义

子智能体定义放在 `agents/`，例如 `agents/code-reviewer.md`、`agents/plan-executor.md`。
派发时把契约作为任务描述传进去。

## 退出标准

- [ ] 每个派发都包含四要素契约
- [ ] 每个产出都用证据验收过（不是只读自述）
- [ ] 主上下文没有残留子智能体的搜索噪音
- [ ] 合并后跑过一次完整 `verify.sh`

## 反模式

- 派发时不给验收标准，只给"帮我实现这个"
- 多个子智能体同时改同一个文件
- 完全信任子智能体的"已完成"结论
- 用子智能体处理需要与用户反复确认的需求
