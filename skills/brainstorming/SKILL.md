# 技能：brainstorming（澄清与设计）

## 何时使用

- 需求只有一句话，且细节会影响实现方向
- 有多种合理解法，取舍需要用户拍板
- 涉及新依赖、新概念、新数据模型
- 用户说"我想要个 XX"，但没说边界

**不适用**：拼写、注释、格式化、重命名等无行为变化的改动——直接做。

## 核心原则

1. **一次只问一个问题**。连着抛五个问题等于把人劝退
2. **先问"为什么"，再问"怎么做"**。目标错了一切都错
3. **给出候选而非空白**：问"你更倾向 A 还是 B（各自代价）"，而不是"你想怎么做"
4. **能自己查的就自己查**。读代码/搜索能回答的，不要问用户
5. **不问能通过删功能绕开的问题**。先确认最小可用范围

## 步骤

### 1. 复述与假设

用自己的话复述需求，列出你做的假设，请用户纠正。
假设不澄清就写代码，是最贵的错误。

### 2. 定位现状

搜索相关代码与规约，回答：现在是怎么实现的？这次会碰哪里？
**先搜再问**：搜索工具查过的部分，不要重复问用户。

### 3. 逐项收敛（每次一个）

| 必须问清的 | 不必问的 |
| --- | --- |
| 谁会用、什么场景 | 变量怎么命名 |
| 必须满足的硬约束（性能、兼容、合规） | 内部实现细节 |
| 什么算做完（可观察的验收） | 你打算怎么组织文件 |
| 明确不做什么 | 用哪个设计模式 |

### 4. 给方案（2-3 个）

每个方案写：**做法 / 代价 / 放弃它我们会失去什么**。
不要只列优点，权衡信息全在缺点里。

### 5. 落成规约

把结论写进 `openspec/changes/<id>/proposal.md`，含范围与非目标。
**到此为止，不写实现代码。**

## 退出标准

- [ ] 能用三句话说清：要解决什么、做哪些、不做哪些
- [ ] 每条待做项都有可观察的验收方式
- [ ] 用户明确确认了方案（而非"你觉得行就行"）
- [ ] 已写入 `proposal.md`，且 `npx openspec validate` 无结构错误

## 反模式

- 一口气问 8 个问题
- 自己拍板技术选型然后直接开写
- 把"怎么做"和"做什么"混在一个问题里
- 澄清完不落文档，靠对话记忆推进（下个会话就没了）
