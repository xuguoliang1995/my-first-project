# 技能：executing-plans（执行计划）

## 核心命题

计划的价值在于**约束执行顺序**，而不是写完之后被丢在一边。
执行期的自由度只允许出现在"怎么实现"，不允许出现在"做什么、做几件"。

## 执行循环

对 `tasks.md` 中的每一项：

```
1. 读该任务的验证方式
2. 写失败的测试（test-driven-development）
3. 写最小实现让它转绿
4. 运行该任务自己的验证命令
5. 立即勾选 checkbox，不要攒到最后
6. 记录偏差（如有）
```

## 偏差处理

| 情况 | 处理 |
| --- | --- |
| 任务比预期大 | 停下来拆成两个任务，更新 `tasks.md`，再继续 |
| 发现方案不可行 | 回到 `writing-plans`，更新 `design.md` 并说明为何改 |
| 发现范围外的问题 | **记录，不改**（写进 `docs/retro/` 或新开变更） |
| 验证失败且 3 轮修不好 | 停下来说明卡点，请求协助，禁止硬试 |
| 用户中途改需求 | 停下来确认，更新 proposal，不要"顺手一起做" |

## 上下文管理

任务很多时，主上下文会被搜索过程污染：

- 独立任务 → 派给子智能体（`subagent-driven-development`）
- 主上下文只保留：做了什么、改了哪些文件、验证结果、遗留项
- 每个检查点向用户汇报一次，不要闷头走完 20 个任务

## 检查点节奏

至少在这些时刻停下来验证：

1. 每组任务（能力）完成后 → 跑一次 `verify.sh`
2. 全部任务完成 → 跑完整验证并写 `verification.md`
3. 任何一次"我改动了契约（`packages/shared`）"之后 → 立即跑全量

## 退出标准

- [ ] `tasks.md` 全部勾选，或有明确记录的未完成项
- [ ] 每个任务都执行过它自己的验证命令
- [ ] `bash scripts/verify.sh` 退出码 0（不是 2）
- [ ] 偏差与范围外发现已记录

## 反模式

- 一口气写完所有代码，最后统一验证
- 任务没勾选，靠记忆判断进度
- 边执行边改计划，且不更新 `tasks.md`
- 遇到失败就改断言/跳过测试
