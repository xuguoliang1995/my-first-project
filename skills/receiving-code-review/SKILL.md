# 技能：receiving-code-review（接收评审）

## 核心态度

评审意见是**假设**，不是判决。你要做的是：

1. 验证它是否成立（读代码、写测试、跑命令）
2. 成立就修，并留下证据
3. 不成立就说清依据，不要沉默照改

两种极端都错：**辩护式反驳**（"这不是问题"）和**无条件服从**（改了反而更糟）。

## 处理流程

### 1. 分类

| 类型 | 处理 |
| --- | --- |
| P0/P1（缺陷、安全） | 立即修，补测试，重跑验证 |
| P2（结构、测试缺口） | 修，或明确记录为后续变更并说明理由 |
| P3（风格、命名） | 对照 `harness/rules/10-code.md`；规范没写就不必改 |
| 范围外要求 | 不改，记录到 `docs/retro/` 或新开变更 |

### 2. 逐条验证

对每条意见：

```
读相关代码 → 构造能证实/证伪的用例 → 运行 → 记录结论
```

不要靠"看起来像是有问题"就改。也不要靠"我觉得没事"就驳回。

### 3. 修改

- 先写失败测试复现问题（缺陷类）
- 修完重跑该测试 + 全量 `verify.sh`
- 一个意见一个提交（或一组相关意见一个提交），便于回溯

### 4. 回复

```markdown
### P1 — 已修
- 现象：<复现方式>
- 根因：<证据>
- 修改：<文件:行>
- 验证：<测试名 + 输出摘要>

### P2 — 不改，理由如下
- 结论：属于既有行为，改动会超出本次变更范围
- 建议：已记录到 openspec/changes/<新id>/proposal.md
```

## 禁止

- 为了让评审通过而削弱断言
- 不读代码就照改（可能引入新缺陷）
- 把"我改了"当成"我验证了"
- 收到意见后扩大改动范围

## 退出标准

- [ ] 每条意见都有明确处置（修复 / 驳回 + 理由 / 转后续变更）
- [ ] 缺陷类意见都有回归测试
- [ ] `bash scripts/verify.sh` 退出码 0
- [ ] 回复中给出的是证据，不是态度
