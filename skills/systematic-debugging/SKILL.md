# 技能：systematic-debugging（系统排障）

## 铁律

**先证明根因，再改代码。** 猜测式修改会让问题从一个地方转移到另一个地方，
并且污染你的因果判断——改了三处后即使好了，你也不知道是哪处起的作用。

## 阶段一：收集事实

不查代码，先看现象：

- 完整错误信息与堆栈（**不要只看第一行**）
- 复现步骤：什么输入、什么状态、必现还是偶现
- 最近的变化：`git log`、`git diff`、依赖升级、配置调整
- 环境差异：本地能跑线上不能？版本？环境变量？

**产出**：一句话描述"什么条件下发生什么"。

## 阶段二：提出假设

列出 2-3 个可能原因，按概率排序。每个假设都要能被观察证伪：

| 假设 | 验证方式 |
| --- | --- |
| 输入为空导致解构抛错 | 加日志打印入参 / 写一个空输入的测试 |
| 时区导致日期比较失败 | 用固定时区跑测试 |

一次只验证一个假设。同时改多个变量 = 无法归因。

## 阶段三：二分定位

- 二分法：注释掉一半逻辑，看问题是否消失
- 从数据流入口开始，逐段打印中间值，找到**第一个**不正确的值
- 找不到就缩小范围：能用一个最小复现用例复现吗？能，问题就在被删掉的代码里

**产出**：`文件:行号 + 具体错误的中间值 + 为什么它错了`

## 阶段四：修复与防复发

1. **先写一个能复现该缺陷的失败测试**
2. 修根因，不修症状（症状修复 = 加 try/catch 掩盖）
3. 测试转绿
4. 检查同类问题：同样的模式在别处存在吗？
5. 记录到 `docs/retro/`：现象、根因、为什么没早发现

## 常见反模式

| 反模式 | 后果 |
| --- | --- |
| 加 `try/catch` 让报错消失 | 错误变成静默，更难排查 |
| 随机加日志到处跑 | 噪音淹没信号 |
| 一次改多处再验证 | 无法归因 |
| 只修复表层症状 | 换个输入又崩 |
| 不写回归测试 | 下个月原样复发 |
| 升级依赖"试试看" | 引入新变量，问题更复杂 |

## 卡住时

连续 3 轮假设都被证伪 → 停下，不要硬试：

1. 把已知事实完整写出来（写给用户看）
2. 明确说明卡在哪、还缺什么信息
3. 请求环境、日志或用户操作路径的补充

**硬试的成本永远高于承认卡住。**

## 退出标准

- [ ] 根因被证据（日志/中间值/最小用例）证明，不是推测
- [ ] 有对应的回归测试，且曾真实失败
- [ ] `bash scripts/verify.sh` 退出码 0
- [ ] 根因与教训已记录
