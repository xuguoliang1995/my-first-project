# 技能：requesting-code-review（发起评审）

## 评审的顺序（不要一上来挑命名）

1. **它做的是需求要的吗？** —— 对照 `proposal.md` 的验收点
2. **它会坏吗？** —— 边界、错误、并发、空值
3. **它安全吗？** —— 输入校验、鉴权、密钥、注入
4. **它有没有越界？** —— 改了不该改的文件
5. **最后才看可读性**

顺序颠倒的评审会产出"命名建议 10 条，漏掉 1 个空指针"。

## 发起前先自检

把自己当成评审者，先过一遍这张表，能自己修掉的不要浪费一轮评审：

- [ ] 对照 proposal 的验收点逐条确认
- [ ] 跑过 `bash scripts/verify.sh`，退出码 0
- [ ] `git diff` 逐行看过，没有意外改动
- [ ] 没有 `any`、没有 `catch {}`、没有调试残留
- [ ] 新增文件都在变更范围内

## 提交评审时要给的信息

```
变更：openspec/changes/<id>
意图：<一句话>
改动：<文件列表 + 各自职责>
验证：<verify.sh 输出摘要 + 退出码>
关注点：<你最不确定的 1-3 处，请重点看>
```

**不给关注点的评审 = 让对方从零猜。**

## 高危信号（P0/P1，发现即阻断）

| 信号 | 为什么危险 |
| --- | --- |
| `catch {}` / 忽略返回的错误 | 静默失败，线上排查地狱 |
| 外部输入未校验直接用 | 注入、越权、崩溃 |
| 拼接 SQL / 命令字符串 | 注入 |
| `any`、`as` 强转绕过类型 | 类型检查失效 |
| 密钥硬编码或打进日志 | 泄露 |
| 修改了断言 / 跳过测试 | 掩盖真实缺陷 |
| 删除或放宽了已有校验 | 隐蔽的回归 |
| 范围外的大段重写 | 隐性破坏，无法评审 |

## 中危（P2）

- 缺少错误路径与边界的测试
- 函数职责过多、参数过多
- 深层嵌套、重复逻辑
- 有 TODO 但没有关联变更 id 与移除条件
- 依赖方向越界（`packages/shared` 里做 I/O）
- 资源未释放、监听未清理

## 低危（P3，可提但不阻断）

- 命名与术语表不一致
- 注释描述"是什么"而非"为什么"
- 格式不统一（交给工具，不要人来纠）

## 输出格式

按严重度分组，每条包含：**位置 / 问题 / 为什么是问题 / 建议怎么改**。

```markdown
### P1 — `src/x.ts:42` 未校验 `pageSize` 上限
- 问题：用户可传 `pageSize=1000000`，一次拉全表
- 影响：内存暴涨、接口被打穿
- 建议：校验 1 ≤ pageSize ≤ 100，超出返回 400
```

## 评审纪律

- **不把个人偏好当作缺陷**：除非项目规范明确写了
- **不要求改动范围外的东西**：发现就记录为后续变更
- **每条意见可执行**：能被直接改成一段 diff
- **明确结论**：通过 / 有条件通过（列出必修项）/ 打回

## 退出标准

- [ ] 对照 proposal 逐条核对了验收点
- [ ] 所有 P0/P1 已解决或明确标注
- [ ] 给出了明确结论，而不是"再看看"
