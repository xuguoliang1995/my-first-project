# 技能：writing-plans（拆解与计划）

## 何时使用

- 需求已澄清，但实现需要改动多个文件/多个包
- 工作跨会话，需要留下可续接的痕迹
- 存在依赖顺序（A 不做完，B 无法开始）

## 任务粒度判据

一个合格的任务满足全部四条：

1. **一个会话内可完成**（不需要中途等用户决策）
2. **diff 不超过 400 行**
3. **有明确验证方式**（命令、测试名、可观察结果）
4. **可独立回滚**，不牵连其他任务

不满足 → 继续拆。

## 步骤

### 1. 先写验收，再写任务

从「用户能观察到什么」倒推。任务清单必须覆盖全部验收点。

### 2. 分组而非平铺

按**能力**分组，不按文件类型分组：

```
## 1. 数据契约         ← 先定类型，后续依赖它
## 2. 后端能力
## 3. 前端接入
## 4. 收尾与文档
```

组内顺序体现依赖：契约 → 实现 → 接入 → 收尾。
**测试与文档写在各自组内，禁止堆到最后单独一组补。**

### 3. 每条任务写三件事

```markdown
- [ ] 2.1 实现查询任务的接口
      验证：`npm test -- task.query` 转绿
```

做法一句话 + 验证一句话。没有验证方式的任务不算任务。

### 4. 标出风险与阻塞

在清单末尾记录：不确定的技术点、需要用户决定的事、可能返工的地方。
提前暴露风险比事后解释便宜。

### 5. 与 openspec 对齐

- `tasks.md` 必须建立在 delta spec 与 `design.md` 之上，避免"边想边写"
- 用 `npx openspec status --change <id>` 确认产物齐全
- 需要官方写作指引时：`npx openspec instructions tasks --change <id>`

## 计划产物放哪

| 场景 | 位置 |
| --- | --- |
| 有 openspec 变更 | `openspec/changes/<id>/tasks.md` |
| 跨多个变更的长期计划 | 拆成多个 openspec 变更，在各自 `proposal.md` 写明前置/后续变更 id；不另设计划目录 |

## 退出标准

- [ ] 每条任务都有 checkbox + 验证方式
- [ ] 任务之间依赖顺序明确，无循环依赖
- [ ] 第一个任务小到可以立刻开始（不是"搭建整个框架"）
- [ ] 风险项已显式列出

## 反模式

- 「实现后端」这种巨型任务
- 任务顺序按文件而不是按能力
- 把"写测试"和"写文档"堆在最后
- 计划里塞满实现细节（那属于 design.md）
