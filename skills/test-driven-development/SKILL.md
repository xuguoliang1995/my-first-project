# 技能：test-driven-development（测试先行）

## 铁律

```
红灯 → 绿灯 → 重构
```

**没有见过红灯的实现，不算完成。** 如果测试一写完就直接通过，
说明它没在验证新功能——要么断言写错了，要么测试没跑到目标代码。

## 循环

### 1. 红灯（Red）

写一个**恰好一个**失败测试：

- 测试名描述行为：`returns 404 when task does not exist`
- 断言外部可观察结果，不断言内部调用
- 运行它，**确认失败原因是"功能不存在"**，而不是语法错误或测试框架配错
- 只写一个。一次写五个测试再一起跑，是伪 TDD

### 2. 绿灯（Green）

写**最少**的代码让它通过：

- 允许丑陋，允许硬编码，允许只有一个分支
- 不写"以后可能要用"的抽象
- 运行，确认通过，且**其他测试没被弄红**

### 3. 重构（Refactor）

测试保持绿的前提下：

- 消除重复、改善命名、抽取函数
- 每步都重跑测试，不要攒着一起改

### 4. 下一个测试

从「下一个最明显的失败场景」继续，优先补边界与错误路径。

## 必测的四类场景

| 类型 | 例子 |
| --- | --- |
| 正常路径 | 合法输入返回期望结果 |
| 边界值 | 空数组、0、最大长度、单元素 |
| 错误路径 | 非法输入、依赖抛错、超时 |
| 状态/权限 | 未登录、无权限、重复提交 |

## 判断测试好坏

问三个问题：

1. **删掉这段实现，测试会红吗？** 不会 → 测试没意义
2. **改了实现但行为不变，测试会红吗？** 会 → 测试耦合了实现细节
3. **测试失败了，能立刻知道是哪里的问题吗？** 不能 → 粒度太大

## 严禁

- 为了让测试通过而修改/删除断言
- 提交 `test.skip` / `.only`
- 先写实现再补测试并声称 TDD
- 用 mock 覆盖掉全部真实逻辑（测了个寂寞）
- 断言"函数被调用了 1 次"这类实现细节

## 与验证回路的衔接

- 单个测试：由包自己的 `test` 脚本执行
- 交付前：`bash scripts/verify.sh` 必须退出码 0（2 = 无法验证）
- 证据写入 `openspec/changes/<id>/verification.md`

## 退出标准

- [ ] 每个新增行为都有对应测试
- [ ] 每个测试都曾真实失败过
- [ ] `bash scripts/verify.sh` 退出码 0
- [ ] 无 skip / only / 注释掉的断言
