# 20 — 测试规范

## 铁律：测试先行

顺序不可颠倒：

```
1. 写一个失败的测试 → 运行 → 看到它失败（失败原因是"功能不存在"，不是语法错误）
2. 写最少的实现让它通过 → 运行 → 看到它变绿
3. 重构（测试保持绿）
```

**没有见过红灯的测试，不算测试。** 先写实现再补测试，等于事后自我说服。

## 测试分层

| 类型 | 占比 | 覆盖什么 | 速度要求 |
| --- | --- | --- | --- |
| 单元测试 | ~70% | 纯函数、领域逻辑、边界条件 | 单测 < 10ms |
| 集成测试 | ~25% | 接口、数据库、模块协作 | 单测 < 1s |
| 端到端 | ~5% | 关键用户路径（1-3 条） | 可慢 |

## 每个需求必须覆盖

1. **正常路径** —— 最常见的输入
2. **边界值** —— 空、0、最大值、超长、只有一个元素
3. **错误路径** —— 非法输入、依赖失败、超时
4. **权限/状态** —— 未登录、无权限、重复操作

## 测试质量

- 测试名描述行为：`returns 404 when task does not exist`，而不是 `test delete`
- Given / When / Then 三段，用空行分隔
- 一个测试只断言一件事，失败时能直接定位
- **不测实现细节**：断言外部可观察行为，不断言内部函数被调用几次
- 禁止 `skip` / `only` / 注释掉断言提交
- 测试互相独立，不依赖执行顺序，不共享可变全局状态

## 反模式（出现即返工）

- 为了让测试通过而修改断言
- 测试里复制一份实现逻辑做对比（同义反复）
- 只测 mock，真实实现一行没跑
- 覆盖率当作目标而不是结果指标

## 与验证回路的关系

`scripts/verify.sh` 依次探测各包的 `typecheck` → `lint` → `test` → `build`：

- 全部阶段被跳过 → 退出码 **2（无法验证）**，不得表述为通过
- 任一阶段失败 → 退出码 1
- 至少一个阶段真实执行且全绿 → 退出码 0

测试证据必须写入 `openspec/changes/<id>/verification.md`。
