# 30 — 安全与提交

## 安全底线

1. **密钥永不入库**。凭据只走环境变量；`.env*` 已被 `.gitignore` 忽略，提交前自查
2. **所有外部输入视为不可信**：请求体、URL 参数、Header、文件名、上传内容
   —— 校验类型、长度、范围、枚举，再使用
3. **不拼接查询**。数据库访问一律用参数化查询 / ORM 绑定
4. **不在日志里打印敏感信息**（token、密码、身份证、完整手机号）
5. **鉴权在服务端**。前端的隐藏按钮不是权限控制
6. **新增依赖需说明理由**。禁止引入无维护、来源不明的包；优先用标准库
7. **AI 生成代码同样适用以上全部规则**。不因为"是生成的"就降低审查标准
8. **认证类功能默认按全量规格处理**：必须写 `design.md` + ADR（见 `docs/decisions/0001`）

## 依赖审查要点

- 该包是否必需？能否用标准库或已有依赖替代？
- 周下载量、最近发布时间、是否有已知漏洞？
- 引入的是运行时依赖还是开发依赖？是否显著增加产物体积？

## 提交规范

Conventional Commits，中文正文可，类型前缀固定：

```
feat(scope):     新功能
fix(scope):      缺陷修复
refactor(scope): 重构（行为不变）
test(scope):     测试
docs(scope):     文档
chore(scope):    构建/依赖/工具
```

要求：

- 标题不超过 50 字符，祈使句，不加句号
- 一个提交只做一件事；同时改行为和重构 → 拆两个提交
- 提交信息说明**为什么**，diff 已经说明了**是什么**
- 正文引用变更 id：`Refs: openspec/changes/<id>`

## 分支与合并

- 分支名：`feat/<变更id>`、`fix/<简述>`
- 主干保持可运行：任何时刻 `verify.sh` 在主干上不得为 1
- 合并前必须：验证通过（退出码 0） + 变更已归档或明确保留 + 无 TODO 遗留
- 禁止 `--no-verify`、禁止强推主干、禁止直接提交到主干（单人初始化场景除外）

## 提交前自查清单

- [ ] `bash scripts/verify.sh` 退出码为 0（不是 2）
- [ ] `git diff` 逐行看过，没有意外改动
- [ ] 没有残留调试代码（`console.log`、`debugger`、临时注释）
- [ ] 没有 `.env`、密钥、大文件被误加
- [ ] 提交粒度合理，信息可读

`bash scripts/install-hooks.sh` 会把这份清单固化成 pre-commit 闸门。
